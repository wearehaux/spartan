Theme architecture + delivery plan · 12 October 2026

One system.
Independent controls.

A practical plan for brand, theme, style and density in Spartan. Keep the parts that work. Make every component’s response explicit.

Code-first plan agreedLive Figma + local code inspectedNo library changes

Code first, Figma afterward in stable batches. The delivery sequence is agreed; proposed token changes still need their individual decisions. Read the diagrams and highlighted recommendations first. Expand the code examples when you need implementation detail. The interactive example illustrates the proposal; it is not a production component preview.

01 / THE RECOMMENDATION

Keep the controls separate.
Connect them at the component.

A theme is the complete configuration. Style is just one part of it. Atlas or Selene should not also decide your brand color, information density, or light/dark setting.

Recommended: retain the existing seven collections and identities for now. Clarify their ownership, finish the component bindings, and simplify the controls shown to product designers. Add a brand-independent system color group inside Semantic Color. Do not delete Primary during this planning phase.

Global or container setting

“Make this screen Selene.”

Variable modes change radius, surface treatment, borders and selected effects. Children inherit the setting.

Component setting

“Make this field Outlined.”

Appearance is a local choice. It overrides the default surface treatment while retaining agreed style properties such as radius.

Existing axis contract: Spartan variables and token contract. The ownership recommendations in this report are proposed.

03 / WHERE EACH DECISION LIVES

Each property has one owner.

Do not put every mode on every collection. Component tokens can remain in one Value mode and reference a value from Density or Style. The referenced collection supplies its selected mode.

CollectionModesOwns
01 PrimitivesValueRaw named palettes, fixed spacing scale, radii, type values. A shared blue palette keeps its identity.
02 Primary retainBlue / Purple / Orange / SkyBrand palette selection. “Brand” can be the designer-facing label; preserve API names and IDs during migration.
03 Semantic ColorLight / Dark / Light High Contrast / Dark High ContrastMeaningful color roles. Include separate Brand, System, Status and Neutral groups.
04 Semantic FoundationValueStable typography, border and geometry roles. No second color system here.

The collection is storage. The role is the meaning. System color can be a group inside Semantic Color. It needs its own collection only if users must select an additional independent system-palette mode.

04 / BRAND IS NOT SYSTEM FEEDBACK

Change the product accent.
Keep control feedback predictable.

Use a dedicated brand palette for primary actions and intentional branded surfaces. Use a separate system palette for checked controls, selected options and focus. Both still need suitable tones in Light, Dark and High Contrast.

Do not recolor the shared blue primitive ramp to rebrand. It already feeds system controls. Create or configure a dedicated brand ramp instead. A brand update needs its full tonal range and foreground pairs, not one replacement hex.

OptionWhen it fitsTradeoff / recommendation

One dedicated brand ramp in PrimitivesA product-specific library with one brand.Editing it affects all consumers of that library. No per-frame brand selection. Valid future fork, but alias migration is required first.
Named product brand modesActual multi-brand products, rather than hue experiments.A later evolution of Primary. Preserve old aliases and mode compatibility until consumers migrate.

Reuse the existing semantic roles

Keep color/control/default, hover, active, foreground and track. Repoint color/focus-ring/default toward the system palette after a consumer audit. Separate focus and selected roles can use the same palette without using the same hex.

Check the whole path

Focus-related field borders, shadows and hover treatments can still reach Primary through aliases. Check transitive references. Danger remains danger; system focus must stay visible around a danger control.

Recommendation only: no palette, alias, mode or variable was changed for this report.

06 / DENSITY IS A ROLE MAPPING

Change useful space.
Do not scale the whole interface.

Keep Size and Density separate. Size chooses Small or Base. Density decides the metrics for that size. A Compact Base control is not the same API choice as a Relaxed Small control, even when both happen to be 32 px high.

MetricCurrent Relaxed → CompactRecommended direction
Base / Small control height40 → 32 / 32 → 28 pxKeep these established tiers. Prefer minimum height where content can grow. Do not reintroduce 48 px Large standard controls.
Control horizontal padding / gapBase 16 → 12 / gap 8 → 6 pxGood density levers. Preserve family-specific optical padding.
Base type / line height / icon15 → 14 / 22 → 20 / 20 → 18 pxCurrently changes. Proposed next contract: keep readable type and icons stable by default, reviewing existing differences deliberately.
Surface padding24 → 16 pxMap card and dialog section padding to clear anatomy roles.
Generic row height64 → 56 pxPreserve current uses. Introduce a distinct one-line table-row role if 40 → 32 px is desired; do not shrink multi-line rows globally.
Generic density/space/416 → 16 pxNo density effect today. Keep fixed-scale references predictable and opt content into named density roles.
Typography, radii, colors, shadowsMixed current bindingsDo not apply a blanket density multiplier. Radius belongs to Style, colors to Semantic Color, effects to layer/style roles.
Salesforce

Density can affect layout

SLDS 2 describes spacing and typography hooks. Record forms also adapt label placement: compact labels can move above fields when space is narrow. That form setting does not automatically change arbitrary custom components.

SAP Fiori

Smaller space, stable type

Current guidance keeps font size unchanged. Cozy uses a 44 px touch area; compact rows and toolbars can be 32 px. The hit area can be larger than the visible control.

IBM Carbon

Rows have explicit sizes

Tables use 24, 32, 40, 48 and 64 px rows. The 40 px size is the default; 64 px accommodates two lines. This is a table size contract, not a universal density multiplier.

Carbon data tables

Recommended for Spartan: start with minimum heights, padding and gaps. Keep the primitive scale fixed. Add named roles such as density/menu/item/padding-y, density/form/group/gap and density/chart/legend/gap. These names are proposed, not existing tokens.

Proposed alias recipe. The existing density values are 24/16. Content must remain Hug height in Figma and content-driven in code; padding must not hide long copy.

Charts need two separate decisions

Density can reduce outer padding, legend gaps and tooltip padding. Responsive chart layout decides tick frequency, label placement, minimum plot size, aspect ratio and legend wrapping. Keep series colors, scales, units and data unchanged. Do not shrink labels or remove the legend just to fit.

Carbon’s legend guidance adapts placement and stacking to available space: Chart legends. The separation into two policies is our recommendation.

Small visuals still need usable targets

Keep the interactive hit area separate from visible size. WCAG 2.2 AA uses a 24 × 24 CSS-pixel target minimum with defined exceptions; AAA’s enhanced criterion uses 44 × 44. Use 44 px or more as a touch comfort goal without adding a new Large visual tier. Check neighboring target overlap.

08 / SAME INTENT, DIFFERENT MECHANICS

Figma chooses collection modes.
Code composes settings.

In Figma

Set modes on the screen or container. Keep nested components on Auto so they inherit. A local explicit override is deliberate. Binding a component color or radius to the wrong collection bypasses the intended setting.

In Lit

Use the existing theme API and generated CSS properties. Global tokens can inherit through the host into Shadow DOM. Map anatomy tokens in component CSS where needed. Portals and independently mounted overlays need the theme scope carried to their container.

A practical code example using the current API
import { applyTheme } from '@spartan/components/theme';

applyTheme(document.documentElement, {
  style: 'Selene',
  colorScheme: 'Dark',
  highContrast: true,
  hue: 'Purple',
  density: 'Relaxed'
});

// An intentionally denser data workspace inherits all other settings.
applyTheme(document.querySelector('#data-workspace'), {
  density: 'Compact'
});

// Remove that local decision to inherit again.
applyTheme(document.querySelector('#data-workspace'), { density: null });

The runtime API exists. Each component must still consume the affected tokens. Prefer one density per task area; support for nested settings is not a recommendation to mix densities arbitrarily.

Why a simple CSS alias can fail in a nested scope
/* An inherited alias may already be resolved on the ancestor. */
:root {
  --example-density-height: 40px;
  --example-button-height: var(--example-density-height);
}
.compact {
  --example-density-height: 32px;
  /* Redeclare the consumer here, or resolve locally in component CSS. */
  --example-button-height: var(--example-density-height);
}

The existing generator accounts for transitive mode dependencies and redeclares tokens at relevant mode boundaries. Preserve that mechanism. Arbitrary brand overrides on a subtree need equivalent dependency handling; do not assume changing one inherited primitive re-evaluates every downstream alias.

If a Style option does not appear or does nothing

  1. Check the bound variable.

    At least one layer must consume a variable from the multi-mode collection, directly or through a valid alias path.

  2. Check inheritance and overrides.

    A child explicitly locked to Atlas does not follow a Selene parent. A raw radius does not follow any style.

  3. Check the right control.

    Global Style lives in variable modes. Appearance/Variant lives in component properties. These are different controls.

  4. Check library and code versions.

    Old instances may need a published library update. Generated tokens may be current while component CSS is not.

10 / AGREED DELIVERY PLAN

Finalize in code.
Bring stable components into Figma.

Decision confirmed by Iroshan: use code first as the actual delivery workflow. Figma MCP limits constrain daily editing, so Figma availability must not block Lit development. Complete and review the code implementation, then update Figma in manageable batches. This is a production plan, not only a validation exercise.

The workflow is agreed. Individual token changes, including the future of Primary modes and the proposed density typography rules, remain design decisions to resolve during the code work. This report does not claim those changes have been implemented.

  1. Define the token contract in the repository.

    Start from the latest code and saved Figma evidence. Define names, aliases, mode ownership, component states and allowed overrides. Preserve existing identities and compatibility paths. Map the intended Figma collections from the outset, but do not require a new live Figma session to begin code work.

  2. Implement the token system and finalize representative Lit components.

    Use shadcn names, anatomy, states and composition as the reference. Adapt behavior to Lit and apply Spartan tokens. Begin with Button, Input, Checkbox/Switch and Dialog, then continue into dependent families. Review real rendered components in Storybook and settle their style, density and system-color behavior in code.

  3. Continue code delivery across the library.

    Verify applicable states, keyboard behavior, responsive content, theme inheritance and nested slots. Code that passes its development checks can proceed through the normal branch and release process while Figma remains pending. Do not require a matching Figma component after every code change.

  4. Prepare a stable Figma handoff for each family.

    Record the code revision, exact token and alias definitions, public properties, sizes, state combinations, slot anatomy and reference captures. Keep the existing component issue as the queue entry. If code changes before its Figma batch, update the handoff to the intended revision rather than reconstructing an obsolete version.

  5. Update Figma in batches when capacity is available.

    Before the first token import, resolve the importer schema and alias gaps and verify it in a disposable file. These checks gate Figma writes, not code progress. Group shared token changes and related components to reduce repeated reads and writes. Preserve variable and component IDs, existing instance properties and protected 🟢 pages. Finish each batch with focused structural and visual checks, and record the exact checkpoint if the MCP limit interrupts it.

  6. Close the two tracks independently.

    Record development evidence when the code is ready and Figma evidence when that batch is verified. Keep one issue per component with separate Dev and Figma labels. Use Agent Done after agent work according to the project workflow; mark the overall component Done only when both tracks meet their completion rules. Mark a Figma page 🟣 only after its own checks pass.

One-way delivery: the approved token data and Lit component define the implementation; Figma represents that stable contract. A Figma limitation becomes a documented mapping or representation gap. It does not silently rewrite the tested code or imply that token sync creates nested components automatically.
