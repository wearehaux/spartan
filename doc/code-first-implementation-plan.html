02 / THE FIRST CODE TASK

Make code ownership real.

The repository’s stated direction is Git-owned tokens, but the inspected build still generates the token source from a saved Figma export. Agents must fix that authoring path before restructuring tokens.

Current behavior: pnpm tokens:build runs tokens:import, which overwrites tokens/source.json. tokens:check also expects source to match the saved snapshot. Hand-editing that generated source today can be undone by the next build.

Select one canonical authored file during implementation. Keep generated files clearly distinguished from authored definitions.

  1. Reconcile the latest dev work and establish a baseline before editing. Preserve unrelated work and existing public token names.
  2. Remove automatic Figma import from normal builds. Keep import as an explicit, reviewable migration operation.
  3. Let new code tokens exist before a Figma variable ID exists. Preserve known IDs through optional binding metadata or a separate identity map; never invent IDs.
  4. Validate the authored token graph and generated CSS. Move comparison with Figma into a separate drift report.
  5. Prove that a deliberate source change survives repeated builds and that initial generated values remain equivalent before intentional design changes.

Observed files: package.json, scripts/import-figma-tokens.ts, scripts/check-tokens.ts, lib/figma-tokens.ts. This plan does not modify that pipeline.

03 / DELIVERY SEQUENCE

Seven phases.
Useful code ships along the way.

These are ordered work packages, not seven new status labels. Reuse current Linear work where it exists. Reconcile newer branch work before rebuilding any component.

  1. Start here

    Establish Git-owned token authoring

    Implement the pipeline transition above, preserve compatibility, and make snapshots evidence rather than the default authoring source.

    Exit evidence: independent token edits survive builds; generated CSS is reproducible; invalid aliases and cycles fail; no Figma access is needed to add a valid token.
  2. Shared foundation

    Implement the theme and component token contract

    Set ownership for brand, system feedback, semantic modes, density and visual styles. Define component aliases and the supported override rules. Keep existing public values until their migration is deliberately resolved.

    Exit evidence: complete supported mode values, correct nested inheritance, explicit migration differences, and documented family recipes. Decisions remain distinct from implemented capabilities.
  3. Production components

    Finalize the foundational controls in Lit

    Reconcile Button, Icon Button, Input, Checkbox, Radio and Switch, plus shared icons and field structure. Include Dialog early to prove composition and overlays. These are retained production components, not disposable visual experiments.

    Exit evidence: Storybook shows the applicable variants and states using Spartan tokens; behavior, focus, content growth, styles and densities are checked.
  4. Family by family

    Complete dependent components

    Continue through forms, menus and navigation, surfaces and overlays, feedback, tables and charts. Each component consumes verified code prerequisites. An unfinished Figma track alone does not block dependent code.

    Exit evidence: family-level composition works, nested items own their states, slots remain reusable, and each component has its own development evidence.
  5. Throughout code work

    Review and release code incrementally

    Review real components in Storybook. Follow the existing feature branch, dev and main release rules. Prepare a stable handoff at each completed family; continue code delivery while Figma remains pending.

    Exit evidence: the tested revision and checks are recorded. Code completion, merge, release and deployment are reported as separate facts.
  6. Before Figma writes

    Prepare the Figma import bridge

    Extend the custom plugin to support the production schema, cross-collection aliases and identity preservation. Preview diffs and verify repeat application in a disposable Figma file. Plugin development can run alongside later code families once the token schema is stable.

    Exit evidence: real Figma import works, preserves IDs and aliases, and does not duplicate variables when repeated. This gate applies to Figma writes, not code release.
  7. As capacity allows

    Build and verify stable Figma batches

    Apply shared token changes, then construct component families against a pinned code revision. Preserve existing instance links, properties and 🟢 pages. Verify structure and appearance before marking a completed page 🟣 for review.

    Exit evidence: the Figma track identifies the matched code revision, verified nodes, remaining gaps and review marker. Full component completion requires both tracks.
04 / REPEAT FOR EVERY COMPONENT

From reference to a working Spartan component.

Input to the work

A small, explicit component contract

  1. Read the existing issue, implementation and recorded design constraints.
  2. Inspect the relevant shadcn source and examples; record the version or commit used.
  3. List anatomy, properties, events, slots, sizes, semantic variants and meaningful state combinations.
  4. Map each visual property to its owner: Style, Density, semantic role or component anatomy.
Output of the work

Code that is ready to use

  1. Implement native Lit behavior and composition with static styles and generated --sp-* tokens.
  2. Review actual controls in Storybook and refine their design there.
  3. Verify supported states, keyboard access, names, focus, disabled behavior, long content and resizing.
  4. Record evidence and prepare the Figma handoff in the same component issue.

Adapt shadcn deliberately. Preserve useful names and composition concepts. Reimplement framework-dependent behavior for Lit; React hooks, context and portal behavior are not automatically preserved by translating JSX. Do not introduce a second token system by copying shadcn’s raw colors and dimensions.

A passing token matrix proves token resolution. It does not prove that every component consumes the right tokens or behaves accessibly. Keep both kinds of evidence.

05 / MAKE FIGMA WORK RESUMABLE

One stable handoff.
Small batches, fewer repeated calls.

Use the existing component issue as the handoff record. Do not create a second component issue simply because its Figma work will happen later.

Revision
Code commit or release, token version and the source reference used.
Contract
Properties, variants, states, sizes, events and slots. Identify nested items and fixed controls.
Bindings
Exact token keys, aliases, collection/mode mapping, known variable IDs and any required text/effect styles.
Evidence
Storybook links, verified state captures, checked configurations and development test results.
Scope
Target Figma pages and nodes, protected 🟢 pages, existing instances and shared-token impact.
Checkpoint
Completed mutations, returned IDs, latest verification, next operation and unresolved gaps.
  1. Refresh only what can have changed. At the start of a Figma batch, inspect its target nodes, variable identities and dependencies. Reuse earlier evidence for unrelated areas.
  2. Apply shared prerequisites once. Preview and apply relevant tokens/styles before their consumers. Check whether a shared change would affect protected components; use additive mappings or record a scope conflict instead of silently changing them.
  3. Construct reusable anatomy. Use native slots for flexible content, nested item components for repeatable content, and connected icon instances.
  4. Verify the batch. Check bindings, states, style/density changes, slot replacement, resizing and existing instances. Record any unavoidable differences from the code.
  5. Checkpoint when limits interrupt work. Save exact progress in Linear. Resume from that checkpoint next time instead of restarting discovery or claiming completion.

Batch size follows available capacity and component complexity. No fixed daily quota or recurring automation is assumed. Custom token imports reduce repetitive variable editing; component construction still requires deliberate Figma work.

Code pipeline first

Protect authored work from the snapshot import.

  • Inspect the current build and identify the canonical authored source.
  • If the transition is still pending, implement phase 1 before editing token values.
  • Keep Figma mapping metadata and migration evidence without requiring a live Figma ID for every new token.

Selecting a situation only changes this explanation. Nothing is saved or sent.

Agent instructions: AGENTS.md owns the entry rules. .doc/project.md explains the delivery workflow. CLAUDE.md carries matching implementation guidance.
Parallel work: one owner changes the shared token contract. Component agents work against an agreed token revision in separate files. Figma agents consume stable handoffs later; they do not race against active token edits.
Every handoff: state what changed, what was checked, the exact code or Figma revision, and what remains. Update the existing issue’s Dev and Figma tracks separately.
Preservation: keep existing component identities and public contracts until migrations are explicit. Preserve unrelated work and protected Figma pages. Do not restore the retired React workspace.
